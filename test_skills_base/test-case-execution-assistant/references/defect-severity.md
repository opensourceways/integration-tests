# 缺陷严重级别判定

仅在用例【不通过】时填写。5 级严重度，互斥：

## 致命（Critical）

- 系统崩溃、宕机、数据丢失、不可恢复
- 核心主流程完全不可用（登录失败、支付不通、注册阻塞、Robot 完全不工作）
- 严重安全漏洞：SQL 注入成功、XSS 执行、越权访问敏感数据、Token 泄露
- 资金损失、合规违规、隐私数据外泄

**示例**：登录接口对任意密码返回 200 + 有效 token。

## 严重（Major）

- 核心功能可用但行为明显错误，无变通方案
- 关键业务规则失效（金额计算错、权限校验失效、状态机错跳转）
- Robot 关键命令静默丢弃（如多人 /assign 既不分配也不报错）
- 影响大量用户但有变通方案
- 性能严重退化（响应时间增长 10×、并发崩溃）

**示例**：Robot 对 `/assign @a @b` 多人命令完全静默，既未分配也未发提示评论，用户无任何反馈。

## 一般（Normal）

- 次要功能异常或非主路径错误
- 文案显示错误（如英文应为中文、错别字）但不影响功能
- UI 显示异常、布局错乱（不影响操作）
- 默认值不符合设计但可手动修正
- 错误提示信息不友好但不误导
- 兼容性问题（特定浏览器/分辨率）

**示例**：Robot 实测 default_assignee 与配置文档假设不一致；评论文案为英文而非配置的中文模板。

## 轻微（Minor）

- 体验问题、提示信息小瑕疵
- 文案标点、空格、大小写不规范
- 排版、对齐、颜色细节偏差
- 不影响功能也不影响理解

**示例**：Bot 评论 markdown 中 `***user***` 三个星号渲染为粗斜体，与文档约定的双星号粗体略有差异。

## 建议（Enhancement）

- 改进性建议，非缺陷
- 体验优化、可访问性增强、性能微调
- 报错提示更友好的措辞
- 增加帮助文档链接

**示例**：建议 Robot 在 /assign 命令解析失败时给出 specific 提示（"用户不存在" vs "命令格式错"），而非当前的静默处理。

## 判定矩阵

| 影响范围 \ 严重程度 | 不可用 | 行为错 | 体验差 | 完善建议 |
|---|---|---|---|---|
| 核心主流程 | 致命 | 严重 | 一般 | 建议 |
| 次要流程 | 严重 | 一般 | 轻微 | 建议 |
| 边缘场景 | 一般 | 轻微 | 轻微 | 建议 |

## 缺陷说明字段填写模板

```
现象：<原文摘录或简明客观描述>
偏差：<与预期的具体差异>
严重级别：<致命 | 严重 | 一般 | 轻微 | 建议>
建议修复方向：<方向性建议，不写代码>
```

### 示例 1（Robot 多人分配静默）

```
现象：评论 /assign @weixin_55883847 @Guangyue-Xu 后 30s，assignee 未变化，
      评论列表中无 openeuler-ci-bot 任何新评论。
偏差：预期 Bot 应发评论提示 msg_multiple_assignee，实测完全静默。
严重级别：严重
建议修复方向：检查 cmd.go 解析逻辑，当 /assign 后捕获 ≥2 个 @user 时
              应触发 msg_multiple_assignee 评论；或修订设计文档预期与现状对齐。
```

### 示例 2（默认负责人不符）

```
现象：创建无 assignee 的 Issue #18 后等待 15s，assignee 变为 Guangyue-Xu。
偏差：用例预期 assignee 为 xiaoguozhi34，实测为 Guangyue-Xu。
严重级别：一般
建议修复方向：与运维同学核对 repoConfig 实际 default_assignee 配置，
              或修订用例预期与实际配置对齐。
```

### 示例 3（命令大小写敏感）

```
现象：评论 /ASSIGN @weixin_55883847 后 12s，assignee 由 Guangyue-Xu 变为 weixin_55883847。
偏差：用例预期"仅小写 /assign 触发"，实测 /ASSIGN（全大写）也触发分配。
严重级别：一般
建议修复方向：核对 cmd.go 正则是否使用 (?i) 标志；若需大小写敏感则去除该标志，
              或修订用例预期为"命令大小写不敏感"。
```

## 缺陷说明禁止项

- ❌ 只写"失败"、"不通过"、"有问题" 等无信息描述
- ❌ 用主观判断替代客观现象（"用户体验差"、"逻辑有问题"）
- ❌ 直接给代码方案（属于开发的职责，不是测试的）
- ❌ 跨用例归因（"这是上一条用例的问题"→ 应在该用例的「缺陷说明」中记录）
- ❌ 把【阻塞】或【未执行】的原因写进「缺陷说明」时用"缺陷"措辞（应明确写"阻塞原因"或"待补信息"）

# 状态判定规则

## 4 态互斥（优先级降序）

```
阻塞 > 未执行 > 不通过 > 通过
```

多种状态条件同时成立时，按优先级取一。

## 通过

所有步骤实际结果与预期一一匹配，且全部 assertions 评估为 true。

**判定要点**：
- 实际结果"比预期更好"仍判通过（如预期 ≤500ms 实际 100ms）
- 预期为"不应发生 X"，X 确实未发生 → 通过
- 多个预期断言，**全部满足才算通过**，任一不满足直接降级

## 不通过

任一步骤实际结果与预期存在事实性偏差。常见场景：
- HTTP 状态码不符
- jsonpath 值不匹配（equals 失败 / contains 失败 / 类型错）
- 关键字段缺失或为 null
- UI 元素文案、状态、URL 不符
- 数据未按预期落库 / 落错库 / 字段值错误
- 性能指标超出预期阈值

**注意**：
- 用例预期模糊（"显示正常"/"功能可用"）时不可强判通过，应判【未执行】
- 部分通过部分失败 → 整体【不通过】，「缺陷说明」分步骤列出失败点
- 用例预期就是"返回 4xx 错误码"，实际就是 4xx → 通过（不要因为是错误状态码就判失败）

## 阻塞

执行链路中断，无法继续。常见场景：
- 前置条件不满足（账号未注册、数据未初始化、依赖服务不可用）
- 鉴权失败（Token 缺失/过期/无权限）
- 平台 API 不存在（如 gitcode 无组织看板）
- 前序步骤的 capture 失败，后续步骤无法引用
- 工具不可用（curl 不存在、Playwright 未启动、agent-browser 未配置）
- 依赖的前置用例失败导致本用例无法继续
- 第三方服务（短信、支付、推送）不可用

**注意**：
- 阻塞用例**不计入通过/不通过统计**，但需在执行汇总中单列
- 阻塞用例的「缺陷说明」必须写出阻塞的客观原因（不是"用例本身有问题"）

## 未执行

非客观阻塞，是信息或可判定性不足导致无法完成判定。常见场景：
- 用户只贴用例没贴实际现象，且无 agent-exec 块、无可调工具
- 用例的某些步骤用户没说现象（部分缺失也算整条未执行）
- 预期结果模糊无法量化判定
- 用例被显式标记 skip
- 用户提供的现象与步骤对不上号、无法确认对应关系
- 用例字段缺失（缺 ID、缺步骤、缺预期）

**注意**：
- 未执行≠失败，可能是流程外因素
- 「缺陷说明」必须写明"等待 X 信息输入"或"X 字段缺失"
- 用户后续补全信息 → 重新判定为通过/不通过/阻塞

## 部分场景速判

| 场景 | 状态 |
|---|---|
| 前置条件 1 满足、前置条件 2 不满足 | 阻塞 |
| 步骤 1 通过、步骤 2 工具崩溃 | 阻塞 |
| 步骤 1 通过、步骤 2 断言失败、步骤 3 仍能执行且通过 | 不通过（步骤 2 是失败点） |
| 步骤 1 通过、步骤 2 预期是"返回 4xx"、实际就是 4xx | 通过 |
| 用例预期"显示登录成功" 实际响应 `{"code":0}` 无登录确认信息 | 未执行（预期模糊） |
| 工具执行成功但用户提供的截图与工具响应矛盾 | 不通过，「缺陷说明」记录差异让用户裁定 |
| 工具不可用且用户也无现象输入 | 未执行 + 缺陷说明记"等待执行环境" |
| 前置用例失败，后续用例依赖该用例的产物（如 capture 出的 issue number） | 阻塞 |

## 实际结果记录规范

- 与执行步骤一一对应，使用相同编号
- 客观陈述，不带评价词（写"响应耗时 4.2 秒"而不是"响应慢"）
- 涉及数据写入的，记录关键字段值（订单号、用户 ID、issue number）
- 涉及报错的，原文摘录错误码与错误信息
- 长 JSON / 堆栈截取关键片段，用 `...` 省略
- 重试或异步等待的次数 / 时长记录在内（"第 1 次 sleep 12s 后查询 assignee 仍为 null，第 2 次 sleep 12s 后变为 xiaoguozhi34"）
